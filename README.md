# minivllm

A minimal, readable re-implementation of **PagedAttention** and **continuous batching**, written in plain PyTorch so that every mechanism a production engine hides inside a fused CUDA kernel is visible, testable and measurable.

Not a competitor to vLLM. The goal is to be able to answer *"why is it built this way?"* with code and numbers instead of a blog post.

```
                    ┌───────────────────────────────────────────────┐
  prompts ─────────▶│ Scheduler                                     │
                    │  · decode first, then prefill (token budget)   │
                    │  · preempt = drop KV, recompute                │
                    │  · chunked prefill                             │
                    └───────────────┬───────────────────────────────┘
                                    │  [(seq, n_tokens)], cow_ops
                    ┌───────────────▼───────────────────────────────┐
                    │ BlockManager      (the page allocator)         │
                    │  · free list + ref counts                      │
                    │  · copy-on-write                               │
                    │  · prefix cache keyed by block content hash     │
                    └───────────────┬───────────────────────────────┘
                                    │  block_table per sequence
                    ┌───────────────▼───────────────────────────────┐
                    │ ModelRunner                                    │
                    │  k_cache[layers, num_blocks, block_size,        │
                    │          kv_heads, head_dim]                    │
                    │  write by slot_mapping, read by block_table     │
                    └───────────────────────────────────────────────┘
```

中文版见 [README.zh-CN.md](README.zh-CN.md)。

## What is implemented

| Mechanism | Where | Why it matters |
|---|---|---|
| Paged KV cache | [block_manager.py](minivllm/block_manager.py), [paged_attention.py](minivllm/paged_attention.py) | No per-request reservation; memory grows in 16-token pages |
| Copy-on-write | `BlockManager.ensure_capacity`, `fork` | Share full pages between requests, copy only on divergence |
| Prefix caching | `BlockManager.match_prefix` / `register_computed_blocks` | A shared system prompt is prefilled once, not N times |
| Continuous batching | [scheduler.py](minivllm/scheduler.py) | Requests join/leave every step instead of every batch |
| Chunked prefill | `Scheduler._chunk_size` | A long prompt cannot freeze the decode stream |
| Preemption (recompute) | `Scheduler._schedule_running` | Survive memory pressure without OOM or swap |
| GQA / MQA | `_sdpa` (`enable_gqa`) | 0.5B Qwen has 14 query heads but only 2 KV heads |
| Paged attention math | [paged_attention.py](minivllm/paged_attention.py) | `index_select` on a page table == contiguous KV, proven by test |

```powershell
python scripts\demo_generate.py
python scripts\bench_fragmentation.py --kv-pool-tokens 4096 --requests 64
python -m pytest tests\test_block_manager.py tests\test_scheduler.py tests\test_paged_attention.py -q

    --min-output 8 --max-output 512 --distribution heavy_tail

```

The numbers quoted above came from exactly these commands on the machine described
below; the JSON they write lands in `benchmarks/results/`.

The numerics tests run on **CPU/float32** by default (no VRAM, no noise); set
`MINIVLLM_TEST_DEVICE=cuda` to exercise the same assertions on the GPU path.

## Measured on this machine

RTX 4070 Laptop (8 GiB, sharing the desktop), Qwen2.5-0.5B-Instruct in fp16.
Absolute numbers are laptop-scale; the *ratios* are the point.  Every number below
is regenerated by the script named next to it and stored in `benchmarks/results/`.

### 1. Where the memory saving comes from — `bench_fragmentation.py`

Same pool, same requests, two allocators. "reserve" is what a pre-PagedAttention
engine did: hand every admitted request a contiguous `max_model_len` buffer.

```
KV pool: 4096 tokens (256 blocks x 16 tokens), 64 requests of 32 + 8..256 tokens

                                  reserve         paged
max concurrent requests                 2            20
tokens held                          4096          3836
wasted tokens (%)                    90.0%          4.7%
```

10x the concurrency, and the residual waste is only the tail of each sequence's
last page.  Paging removes *external* fragmentation outright; the internal tail is
what `block_size` trades against block-table width.

### 2. Why continuous batching beats static batching — `bench_static_vs_continuous.py`

Identical model, identical code, only `static_batching` flips. 32 requests, 8
slots, output lengths heavy-tailed in 8..512 tokens (most short, a few very long --
a real chat mix).

```
                                     static      continuous
wall time (s)                        94.992          59.921
useful tokens/s                      60.900          96.544
tokens emitted / step                 8.000           6.026
mean latency (s)                    54.177          24.638
p99 latency (s)                     94.981          59.914
mean TTFT (s)                       30.628          13.164

static batching wasted 56% of the tokens it generated
throughput gain: 1.59x   latency 2.2x   TTFT 2.3x
```

The wasted 56% is computed, not idle: a 400-token request drags seven short ones
along for 400 steps. Continuous batching lets them leave the moment they are done
and hands the slot to the queue.

### 3. What prefix caching is worth — `bench_prefix_caching.py`

Six requests sharing a 3285-token system prompt, run one at a time (batching them
together would show nothing -- the cache only helps a request that arrives after
the prefix has been computed and registered).

```
                              prefix off     prefix on
mean TTFT (s)                      0.833         0.214
warm TTFT (s)                      0.779         0.077
shared blocks served                   0          1020

mean TTFT gain 3.9x   |   warm-request TTFT gain 10.2x
```

The first request pays full price (it is the one filling the blocks); every later
request starts decoding almost immediately. The scheduler has to know this: sharing
pages is not enough, `num_computed_tokens` must start after the cached prefix, or
the engine happily recomputes work whose result is already in memory.

## The three questions this repo answers

**1. Where does the memory saving actually come from?**
`bench_fragmentation.py` measures it on the allocator alone. Reserving
`max_model_len` per request leaves the KV cache ~90% empty at realistic sequence
lengths; paging removes the external fragmentation entirely and leaves only the
tail of each sequence's last page, which shrinks with `block_size`.

**2. Why does continuous batching beat static batching?**
Static batching runs a batch until its longest member finishes; every short
request keeps its slot *and its KV memory* for the whole time. Continuous batching
re-decides every step, so a finished request frees its slot for the queue
immediately. The measurement above: 1.6x throughput, 2.2x lower mean latency, at
the cost of a slightly emptier batch (6.0 vs 8.0 tokens per step).

**3. Why is the decode step memory-bandwidth bound?**
At batch 1 the GPU reads the entire weight matrix to produce a single token: the
arithmetic intensity is ~1 FLOP/byte. Batching amortises that read over B tokens.
This is why "just make the GPU faster" does not fix latency, and why `tokens/s`
scales with batch size until KV cache traffic takes over.

## Design notes worth defending in an interview

* **Decode before prefill.** Prefills are bursts of compute nobody sees; decodes
  are the stream a user perceives. Draining decodes first keeps ITL flat, and
  chunked prefill stops a 4k prompt from injecting a 200 ms stall.
* **Recompute instead of swap.** Preempting a sequence drops its KV and re-runs
  its prefill later. For a small model that is one fast pass over the GPU; a swap
  costs a D2H + H2D round trip and, over PCIe, is usually worse.
* **The gather is the cost of not writing a kernel.** `gather_kv` materialises a
  contiguous K/V view through `index_select`, copying memory a fused PagedAttention
  kernel would read in place. It is one kernel launch per batch, not per block,
  but the bandwidth is real -- see the `paged_attention.py` docstring.
* **Block size is a tradeoff, not a constant.** Smaller blocks waste less of the
  tail but make the block table longer and the gather index bigger.
  `test_block_size_does_not_change_results` proves the choice is
  performance-only, never correctness.

## Deliberately not implemented

* A Triton/CUDA PagedAttention kernel (flash-decoding style split-K reduction).
* KV swap to CPU, and beam search / parallel sampling beyond the `fork` primitive.
* Speculative decoding, quantisation, multi-GPU.
* An HTTP server -- [scripts/demo_generate.py](scripts/demo_generate.py) is the entry point.

Each of these is a genuine optimisation, but none of them changes the data flow
this repo is trying to make legible.

## Windows notes

* `flash-attn` and Triton have no reliable Windows wheels -- the pure-torch
  attention here is the reason the whole thing runs at all.
* The KV pool sizes itself from *currently free* VRAM (`gpu_memory_utilization`),
  so close other GPU consumers before benchmarking, or set `num_gpu_blocks`
  explicitly for reproducible numbers.
* Keep the experiment model at 0.5B-1.5B; 8 GiB of VRAM minus a desktop leaves no
  room for 7B in fp16.
